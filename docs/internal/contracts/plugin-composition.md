# Offline staging composition

This contract covers P3 assembly, organization packaging and bootstrap primitives. The [composition plan](../analysis/plan-appsec-advisor-composition-2026-10-18.md) permits offline P2–P4 work before A7 after explicit operator approval. It still requires qualification before release, public cutover, or removal of the existing runtime. The marketplace, existing skills, hooks and public runtime remain on the current implementation. Organization packaging accepts both the existing checkout and an explicit assembled staging input.

## Selected inputs

[`components-lock.schema.json`](../../../schemas/components-lock.schema.json) defines a reviewed selection, not a discovered package inventory. A composition has exactly one host and one engine; additional skill ZIPs, dependency wheels, and build-tool wheels are explicit inputs. Each selection records an HTTPS source identifier, immutable revision, package version, SHA-256, license identification, interface version, required capabilities, and explicit source-to-destination file mappings. Host, engine and skill code require a full committed revision; published dependency/build-tool artifacts may instead identify their reviewed source by `sha256:<digest>`. Source identifiers are provenance records, never download instructions. The builder performs no network request and executes no component code.

Only interface 1 and `unqualified-staging` are accepted. Capability names record required operations; their presence does not establish provider or workflow qualification. Runtime Python minor versions and OS/architecture combinations are selected staging targets, not claims of supported platforms. No production lock or runtime matrix is provided until actual component/dependency artifacts and native platform evidence exist. This format intentionally cannot label an offline build qualified.

The operator supplies artifact files from reviewed committed revisions and verifies their build provenance before approving the lock. A matching digest proves equality with the reviewed artifact; it does not independently prove how an upstream wheel was built. Build tools are locked and delivered for provenance, but are never installed by runtime setup. Source-only packages and implicit runtime dependency resolution are not supported.

## Assembly boundary

Run the builder from the Advisor checkout with the existing Python dependencies already installed:

```bash
python3 scripts/compose_plugin.py --lock /reviewed/components.lock.json --artifacts /reviewed/artifacts --output /staging/new-output-directory
```

The output directory must not exist, and its parent must exist. Failure before assembly validation creates no output. The builder does not read sibling checkouts, copy the repository tree, or rewrite component namespaces. The lock must explicitly select the host manifest, entry skill, host bootstrap, all referenced skill resources, and license texts required by each component's license. Engine implementation remains inside its pinned wheel; engine-owned entry instructions can be selected from that same wheel.

Artifact admission verifies the digest and all ZIP members, including unselected members. It rejects traversal, absolute/drive/stream paths, links and special files, encrypted entries, Windows reserved names, ambiguous separators, duplicate/case-colliding names, file/directory collisions, and non-ASCII paths. File, entry, expanded-byte, total-input and delivered-byte limits are enforced by the builder. Output collisions and reserved generated paths fail closed. Wheel metadata must match the locked version; duplicate distribution names fail. A staging composition cannot include two implementations at the same command path.

Outputs are the staging ZIP, `SHA256SUMS`, license notices, and a delivered [`component-manifest.json`](../../../schemas/component-manifest.schema.json). The archive contains its canonical lock and the same notices and manifest. The manifest identifies selected components and records hashes and sizes of all selected payload files; generated metadata is not self-hashed. Bootstrap verification rejects size mismatches before hashing. ZIP ordering, timestamps and modes are normalized. Build tools and dependency wheels are distributed as opaque verified wheel files, not unpacked into the plugin source namespace.

The host artifact must include `scripts/composition_runtime.py` unchanged from its reviewed Advisor revision. Assembly and organization packaging reject a plugin manifest, bootstrap or progress renderer selected from any other component, even with identical bytes. The command invocation binding is deliberately host-specific; portable skills must not embed `CLAUDE_PLUGIN_ROOT` or checkout-relative engine paths. Portable source preparation is recorded in the [offline evidence](../analysis/composition-offline-evidence-2026-10-18.md); complete host workflow qualification remains pending. Assembling arbitrary legacy skill files does not establish compatibility.

The optional lock selection `"skill_bindings": ["security-score"]` enables the first host binding; `repo-profile` follows the same pattern with the `repo_profile` capability, the public `repo-profile` command and no organization configuration. The lock must select the portable `skills/security-score/SKILL.md`, `dependencies.json`, `references/compatibility.md`, and the host bootstrap. Assembly preserves the portable entry byte for byte as adjacent `WORKFLOW.md`, retaining relative references and source-component provenance, and emits a separate Advisor entry with the pinned invocation. A pre-existing `WORKFLOW.md` is a collision. Other skills and compositions without this selection keep their selected entries unchanged. The binding requires interface 1, scoring version 2, no model calls or model prerequisites, and only the public version, capabilities and score commands; incompatible dependency declarations stop assembly.

The [score staging runbook](../runbooks/composed-score-staging.md) describes explicit setup, direct engine execution and session-only Claude loading. Its real-engine replay establishes local Linux score output and model-free host discovery, not live slash-command execution or full-plugin acceptance.

## Organization packaging boundary

`package_internal_plugin.py --staging /extracted/plugin` consumes an extracted assembler tree instead of a checkout; `--staging` and `--source` are mutually exclusive. The existing checkout path remains available. The packager validates the lock and delivered manifest locally, checks complete inventory and component ownership, verifies hashes and sizes, and compares wheels against their pins. Engine files selected from a wheel must equal their selected wheel members. Unlisted files, ambiguous paths, links, special files, oversized trees and invalid metadata stop packaging before publication. No input-package script is executed.

Branding changes the host manifest, namespace, generated README and host configuration. Namespace rewriting excludes non-host components, bootstrap and composition metadata. Whole skill directories may be removed through package policy, including an engine-owned entry; individual retained engine or portable-skill resources remain unchanged. A final comparison refuses any other change or deletion of protected files. Input trees remain unchanged. The output inventory covers all delivered payload files; host-generated organization outputs use the host's delivery ownership, with organization-added skills and hooks separately recorded in `package-surface.json`.

The output retains the original lock and manifest byte for byte under `organization-source/`; `package-surface.json.composition` points to them. The active lock retains its selected plugin identity, runtime matrix and component records. Its `skill_bindings` selection drops removed skills so the unchanged bootstrap does not require their removed resources. The host manifest carries the branded output name and version. The delivered component manifest records the active lock hash and final payload hashes. The existing lock and manifest schemas apply to both original metadata and delivered metadata. The organization tarball and checksum use the branded output identity; staging tar ordering, timestamps, ownership and modes are normalized.

The staging profile supports organization identity, compatibility, base-mode-only preset declarations, `policy.disable_opus`, `policy.url_allowlist`, banner settings, added skills, hooks, MCP declarations and skill toggles. Packaging splits shared identity, Advisor-owned settings and Analyzer-owned settings under the [organization dispatch schema](../../../schemas/organization-dispatch.schema.json), and emits the engine-only `org-profile/analyzer-config.yaml` envelope separately. `compatibility.core` checks the selected original Advisor core; the envelope independently pins the engine version. The branded output version is neither compatibility input. Disabled skills are physically removed until the runtime policy gate migrates, while their reasons remain in configuration. Unknown toggles and disabling an agent's required internal skill fail. Profile shape, duplicate-key rejection, safe YAML loading without anchors or aliases, hook confinement, MCP credential-URL checks, payload integrity and the final protected-file comparison remain mandatory with `--skip-validation`; that flag skips only optional profile semantic checks. Those checks use the reviewed checkout validator against the selected core version and packaged skill surface.

Settings without a migrated consumer are refused, including data/approval policy, requirements, context, report branding, baseline policy, actor and abuse-case changes, analyst settings, coach settings and preset fields beyond `base_mode`. Use the existing checkout package for these profiles. The accepted score projection has no model execution, report exports or assessment depth. Its Opus restriction cannot authorize a model, and its preset depth remains an inspectable assessment default. A nonempty URL allowlist restricts remote Git targets to an exact hostname or dotted subdomain before Git or credential access. Required unsupported settings are never converted into overridable defaults. Bundling an organization profile never grants engine setup, model use or MCP server execution. `--readme` is unavailable with staging because the README must remain inside the delivered inventory. The [organization packaging guide](../../internal-plugin-packaging.md#package-an-assembled-staging-tree) gives the invocation.

## Organization configuration dispatch

An optionally selected host `config.json` retains banner, display pricing, host log controls and the packaged profile pointer. Its configured default preset remains between environment selection and the profile default, and must exist. Unknown global or nested settings, source-config skill toggles, baseline and external-context blocks are refused until their consumers migrate; profile-based skill toggles use the existing physical surface selection. Display pricing never becomes an engine budget or model price. Packaging never claims that host log limits configure engine logs.

New organization packages require a newly assembled host artifact with the current bootstrap and a pinned Analyzer declaring the exact `organization_config` version-1 capability. Packaging checks the envelope against the public schema inside that verified wheel without executing it; reference-bearing schemas cannot trigger network resolution. It bounds the schema and projection to 64 KiB. An older wheel, missing capability/schema or older bootstrap fails with a reassembly error. Packaging never updates a delivered component in place. The generated engine projection is excluded from namespace rewriting, and retained component bytes still pass the final comparison.

For an active composed profile, the bootstrap invokes the public `organization-config run --config <verified engine projection> -- score ...` API through the exact installed interpreter. The engine validates shape, supported fields, Advisor compatibility, exact engine version and selected preset, checks configuration confinement, and enforces applicable policy before score execution. It preserves score stdout, stderr and statuses. Direct installed Analyzer use with the same explicit configuration enforces the same restriction. Plain CLI calls without that explicit configuration do not acquire a global organization policy.

`organization-config show` and `validate` are available through unbound bootstrap invocation with the packaged projection selected by the host; callers cannot substitute its `--config`. Explicit `--preset` wins over `APPSEC_ADVISOR_PRESET`, which wins over the configured packaged default and then the profile default. Inspection can override the displayed assessment-depth default without changing profile-wide policy. Unknown, empty or missing selections fail. The score command has no assessment-depth override. The existing explicit `--no-org-profile` / `APPSEC_ADVISOR_NO_ORG_PROFILE` selection semantics remain; disabling the selected engine profile does not restore physically excluded skills or change host configuration.

External score profiles are selected only by explicit `--org-profile` or `APPSEC_ADVISOR_ORG_PROFILE`, in that order, before the packaged profile. Relative paths resolve against the plugin root; no repository discovery occurs. The reviewed host artifact must include `schemas/org-profile.schema.yaml` in its verified inventory. Missing validation resources require reassembly. The host rejects source-owned files, links, hard links, nonregular files, unsafe or ambiguous YAML and inputs over 64 KiB, validates the complete Advisor schema, and uses the same ownership split as packaging. External profiles may contain only shared identity, compatibility, base-mode presets and the supported engine policy. Host fields, including banners and build-time surface declarations, fail explicitly because runtime selection cannot reconfigure those consumers. Unsupported engine fields fail even in unselected presets. The existing `--source` path retains broader workflows.

The host runs its verified data adapter with the exact installed interpreter and locked dependencies, then passes only the engine projection through the public `organization-config` API. Its private per-invocation snapshot stays outside sources and the plugin and is removed after success, failure, cancellation or timeout. The engine independently validates compatibility, supported settings and preset selection before source admission. External selection replaces the packaged engine profile and uses CLI/environment preset selection followed by the external profile default; the packaged config default applies only to the packaged profile. Explicit no-profile selection keeps its existing precedence. Empty, missing, malformed or unsupported active selections fail without packaged or upstream fallback. Other engine workflows and additional ledger fields remain explicit compatibility errors; full-assessment and host-consumer migration remain open.

## Explicit runtime lifecycle

After extracting a staging archive into a dedicated installed location, select an existing Python interpreter matching the lock. The bootstrap uses the Python standard library and does not need system `jsonschema`. These are separate actions:

```bash
python3 /installed/plugin/scripts/composition_runtime.py setup --plugin /installed/plugin
python3 /installed/plugin/scripts/composition_runtime.py preflight --plugin /installed/plugin
python3 /installed/plugin/scripts/composition_runtime.py run --plugin /installed/plugin -- score /source/repository --json
```

On Windows, use the selected Python executable instead of assuming `python3`. Arguments and paths containing spaces must be quoted by the invoking host. The launcher passes engine arguments as a list without a shell. The `--` separator distinguishes bootstrap options from public engine arguments. `--runtime-home` is an explicit operator override; storage inside any Git checkout or the plugin is rejected. POSIX storage must belong to the current user and must not be writable by other users; Windows storage stays under the current user's directory, with native ACL qualification still pending. Default storage uses the operating system's user application-data location.

Setup verifies payload integrity, interpreter and platform selection before writing. Runtime identity binds the canonical lock, full Python version, interpreter path, and platform. Setup serializes creation per identity and creates the venv at its final path; no environment is relocated. Installation copies only verified locked engine/dependency wheels into private temporary input storage and uses `pip --no-index --no-deps --only-binary=:all: --require-hashes`. Dependency closure is checked offline afterward; missing wheels or incompatible dependencies fail setup. No source distribution is compiled. Inherited Python paths and pip index/configuration settings are removed from subprocess environments.

The installed engine must report the locked version and interface before a receipt is atomically activated. Setup failure removes its incomplete environment. Existing completed environments are reused only through preflight. A setup lock left by an externally killed bootstrap requires operator inspection; setup does not guess that another process is dead. Concurrent setup is rejected without deleting another process's state.

Required operation declarations must explicitly report boolean `available: true`. A selected score binding additionally checks the portable requirements against the installed engine before activating a receipt. Bound invocations use `run --skill security-score -- <engine arguments>`; each invocation rechecks scoring version 2 and the absence of model calls, and refuses other workflows or a binding absent from the lock. The bootstrap invokes the selected interpreter directly and returns engine stdout, stderr and exit status. The binding does not grant source retrieval, model use or setup permission.

Preflight verifies selection, file hashes and the completed receipt without installing packages, executing the engine, invoking a model, or writing runtime state. `run` requires successful preflight and invokes the exact venv interpreter with isolated Python mode and the public `appsec_analyzer.cli` module. A different engine executable on `PATH` is irrelevant. Model credentials and host prerequisites remain a separate Analyzer responsibility; no qualified model is implied by a successful Python setup.

Invocation has a bounded deadline. On timeout or interruption it attempts bounded public cancellation when an explicit `--output` is supplied, then terminates the launched process tree. This is recovery, not successful assessment completion. Native Windows process-tree cancellation, all selected platform/interpreter combinations, and upgrade/rollback remain unqualified until exercised on those systems. No platform support is declared by Unix tests or mocked platform branches.

## Verification and remaining integration

`tests/test_compose_plugin.py` covers deterministic assembly, delivered inventory, tampering, mismatches, collisions and archive abuse. `tests/test_composition_runtime.py` uses a neutral synthetic wheel to exercise a real offline venv/pip installation outside source checkouts, read-only plugin files, spaces, shadow executables, setup recovery and Unix descendant cancellation. The synthetic wheel is test data only; no plugin build consumes it. These checks establish bootstrap behavior, not installed Analyzer assessment quality or cross-platform qualification.

An internal Linux staging lock and archive exist only as temporary local evidence; their pins are recorded in the [clean composition plan](../analysis/plan-appsec-advisor-clean-composition-2026-10-18.md#committed-implementation-and-installed-evidence). Pending P3/P4 work includes a committed, reviewed composition lock with durable artifacts and reproducible build provenance, dependency/build-tool qualification, remaining portable entry skill bindings and references, public hook/result operations, remaining settings dispatch, permission updates, native platform checks, and archive upgrade/rollback. No existing workflow may switch or producer be deleted merely because these staging primitives pass.


## Assessment configuration handoff

A newly assembled host and engine may use the same admitted organization projection for the existing public `scan` and `assess` commands. The engine must declare those workflows in `organization_config.commands` and boolean `profile_source_validation: true`. Score remains compatible with its declared score-only interface. No additional profile fields become supported: shared identity, Advisor compatibility, base-mode presets and `policy.disable_opus` / `policy.url_allowlist` remain the complete admitted set. Unsupported settings, including fields in unselected presets, continue to fail.

The selected preset seeds assessment depth; an explicit inner `--assessment-depth` wins. The configured scan/model profile and direct CLI budget, output and execution-limit options retain their existing semantics. A Claude Opus selection is clamped before host preflight and by the existing controller. Provider models with an unknown or Opus family fail the restriction before credentials. Git targets and explicitly supplied context/catalog destinations are checked before provider setup or Git access. The existing effective-profile artifact carries the mandatory URL restriction to downstream context consumers; environment allowlists cannot widen it for composition records.

For an external profile the host passes the canonical original selection through outer `--profile-source`, alongside the private engine projection. Analyzer uses its public workflow parser to check both paths against every selected local source. The host refuses caller overrides of `--config` or `--profile-source`; engine control options require exact names. Inner profile-selection flags cannot bypass an active outer profile. The existing explicit no-profile choice is handled by the host and remains explicit when forwarding full-assessment commands. Runtime profile selection does not change the installed host surface.

`organization-config show` and `validate` may receive an optional `-- scan ...` or `-- assess ...` invocation to resolve its settings without accessing sources, credentials or models. Actual `run` retains the existing assessment's authorization and model costs. The `security-score` skill binding still refuses assessment commands. This handoff supplies no new host entry or public runtime switch; the primary entry follows in the next section. Model-free inspection and offline controller tests establish this handoff, not live assessment qualification.

The controller consumes validated organization data through the existing resolver and context-capture contracts. Its metadata uses a content fingerprint and a null filesystem profile path, so temporary host snapshots cannot change resume identity or masquerade as raw actor/abuse-case files. Moving identical configuration preserves identity; changing policy or selected preset does not. Existing legacy resolution is used when no composition data is supplied. Hooks, UI, saved-result consumers and remaining ledger fields stay outside this change.

## Primary-entry source checkpoint

The optional lock binding `appsec-analyzer` now selects the engine-owned primary entry, `claude-code.md` and business-context dialogue from the exact engine wheel. Assembly preserves the original entry as `WORKFLOW.md`, emits the Advisor invocation separately and requires the public assessment, lifecycle, query and export capabilities. Organization packaging checks the preserved workflow against its wheel before branding; the score binding remains score-only. The selected host must include its existing `scripts/runtime/assessment_console.py` renderer as well as the bootstrap.

Bound assessment invocations retain Claude CLI, bounded unattended execution and the existing depth-budget/concurrency/display defaults through the engine's public compatibility option. Start preparation uses the engine's `assessment-entry` operations. The host's `follow --output DIR [--from-end]` action obtains the public live holder and cursored progress, renders milestones and ends independently of the assessment. Output-scoped status, stop, results, query and export do not reload organization configuration; an unavailable external profile cannot block cancellation. Model-backed scan/assess retain the validated profile dispatch and mandatory policy.

This section records a source checkpoint requested before replanning; at that point no updated component artifacts, composition lock or branded archive had been built. The later internal staging artifacts are listed in the [clean composition plan](../analysis/plan-appsec-advisor-clean-composition-2026-10-18.md#committed-implementation-and-installed-evidence). The public plugin entry and existing implementations remain unchanged.


## Separated primary launch settings

The primary binding selects the engine's `--launch-defaults advisor` compatibility layer for depth budgets and concurrency. It passes `--host=claude-cli` and `--non-interactive` separately, and supplies width 72 only without an explicit width. The engine retains `--interactive-launch`, deprecated budget aliases and `--component-workers`; the new and retained entry paths produce the same effective profile and saved-profile identity for equivalent settings. Existing profile/depth precedence and mandatory organization policy remain unchanged. The engine chooses the progress feed for this launch; the host supplies only the selected output directory.

After an authorized stop, the bootstrap's `wait --output DIR --timeout 300` action checks only the public holder with a finite deadline. Exit 0 means the holder is no longer live, exit 3 means it remained live until the deadline, and an invalid or unavailable response fails. Waiting never cancels, cleans or starts an assessment. The skill invokes it once instead of polling through model turns. A progress display may expire independently; the host awaits the owner's notification without an automatic model-managed monitor restart.
